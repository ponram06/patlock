# Current-source audit and local repairs

Historical audit checkpoint. The subsequent implementation pass addresses the
source issues listed here; see RELEASE_STATUS.md and CURRENT_STORAGE.md for
current behavior. VM/hardware acceptance remains pending.

Reviewed current source based on e471e5f and the supplied VM screenshot, rather
than treating the old report as proof. No host builds, tests, registration,
enrollment or installation were performed. This is a bounded static review,
not an exhaustive security certification or a market-ready acceptance.

## Repaired in this checkpoint

- **Disabled credentials were still eligible.** Check() ignored record.disabled
  although ReportResult used Disable() after failed Windows authentication.
  Check() now rejects that flag, so reopening the tile cannot bypass it.
- **Stored verifier doubled as TPM authorization.** Anyone who could obtain the
  record already had the exact authorization value passed to the TPM. Enrollment
  and verification now derive a separate PBKDF2 value with a domain-separated
  salt; that value is wiped and is not stored. This does not prevent offline
  pattern guessing against the stored verifier or prove TPM anti-hammering.
- **ReportResult optional outputs.** Optional null output pointers no longer
  skip processing/cleanup. Each output is checked before writing.
- **Submission completion identity.** FinishSubmission now rejects null, zero
  and mismatched tokens before changing state. The broader persisted one-shot
  submission protocol still needs work, described below.
- **Hardcoded password suggestion.** Removed a specific test-password value and
  password-setting command from enrollment errors. Direct users to Settings.
- **Capture loss.** Losing mouse capture clears any active stroke, including a
  valid partial stroke, instead of allowing its timers to complete authentication.
- **Rendering initialization.** Failed GDI+ initialization declines the dialog.
- **Unsupported PIN fallback.** Removed raw binary authorization passed as
  NCRYPT_PIN_PROPERTY. Microsoft documents this property as a Unicode PIN string;
  it is not interchangeable with the binary PCP authorization property.
- **UI refinements.** Brighter dot outlines/centers, slightly larger idle dots,
  owner-monitor positioning clamped to its work area, and "Pattern accepted"
  instead of claiming Windows sign-in has succeeded before Windows checks it.

### Compatibility

Record version is now **4**. Existing records are rejected; re-enroll inside the
VM after building this checkpoint. Do not manually change the version field or
export the credential record. Re-enrollment replaces the pattern configuration.

## Remaining release blockers

1. **TPM key replacement is destructive before record commit.** ProtectKey deletes
   the old per-SID key before generating a replacement. Later failure can make
   the previous record undecryptable. Use unique key generations, commit the new
   record, and retire the old key only afterward; recover safely from each crash
   boundary. Propagate deletion errors rather than always reporting success.
2. **TPM enforcement and fallback need proof.** Opening the Platform Crypto
   Provider does not establish authorization/anti-hammering behavior. Validate
   wrong authorization, missing/reset TPM, cross-process SYSTEM access and
   property formats from official documentation and tests. Current enrollment
   falls back on any ProtectKey failure, which can conceal implementation errors.
   Explain the selected mode and distinguish unavailable hardware from failure.
3. **One-shot submission is incomplete.** Verify no longer persists disabled or
   a pending-submission state before returning plaintext. A crash before failure
   reporting can allow another stale-password submission. Use an explicit pending
   state, unique token, durable reservation and matching completion, without the
   earlier regression of permanently disabling every successful unlock.
4. **Failed flush does not roll back visible registry changes.** Refresh and
   enrollment can report failure after RegSetValueEx has made refreshed eligibility
   visible. Introduce a commit/activation protocol and fault-inject flush failures.
5. **Input accessibility/DPI.** Fixed pixel geometry, a painted mouse-only link,
   no dedicated accessibility provider and no DPI-change handling remain. Test
   keyboard cancellation/navigation, screen readers, high contrast, display scale,
   mixed-DPI monitors and small displays. Monitor clamping alone is not DPI support.
6. **Hover and timer completion need usability evidence.** Hover can start a
   stroke and a short pause can submit it before the user intends to finish.
   Provide a clearly indicated deliberate input mode and test actual trackpads.
7. **Market readiness needs release evidence.** VM fault tests, real-trackpad
   tuning, installer upgrade/rollback, signing and independent security review
   remain required. A screenshot demonstrates appearance, not these properties.

The current PLAN.md explicitly records Option A: reboot/24-hour freshness is
disabled. This review does not silently restore the old policy. Reconcile older
documents with the current decision and clearly disclose the resulting trade-off.

## VM validation for these repairs

- Build Release x64, inspect warnings and run CTest. New crypto cases check that
  TPM authorization is deterministic, order-sensitive and differs from the verifier.
  These tests are written but not executed by the agent.
- Re-enroll the throwaway local account (record v4), then unlock repeatedly.
- Change the Windows password. Let one Windows submission fail; reopening the
  tile must decline. Built-in Password must continue working.
- Exercise ReportResult with each optional output null in a VM test harness.
- Reject zero/mismatched completion tokens without modifying stored state.
- Lose capture while drawing both short and valid-length strokes; no pending
  timer may verify the abandoned stroke.
- Review dots/text on light/dark wallpapers and multiple monitor arrangements.
- Validate baseline and TPM paths separately. Never claim TPM protection just
  because Available() returns true.
